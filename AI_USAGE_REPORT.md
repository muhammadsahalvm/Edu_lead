## 3. High-Leverage & Useful Prompts

The following prompt structures produced the highest quality engineering output when directing the AI assistant:

1. **Deterministic Business Rules Separation**:
   > *"Implement round-robin counsellor assignment in a dedicated service module rather than in DRF viewsets or Django models. Ensure database row-level locking (`select_for_update`) to prevent race conditions under concurrent submissions, and handle the fallback where no active counsellor is available."*

2. **Single-Pass Analytics Aggregations**:
   > *"Write a single Django ORM aggregation query for the management dashboard that computes total leads, new leads, unassigned leads, and conversion rate without executing N+1 queries. Define conversion rate as (converted / total) * 100 with zero-division safety."*

3. **High-Density SaaS Frontend Polish**:
   > *"Review the frontend as a senior SaaS product designer. Remove excessive cards, gradients, and spring animations. Implement a strict 3-tier visual hierarchy, accessible keyboard focus rings (`:focus-visible`), and non-blocking duplicate alerts."*

## 4. Breakdown of AI-Generated vs. Human-Engineered Code

### Code Initially Generated by AI
- Initial Django model declarations (`Lead`, `FollowUp`, `Course`, `ActivityLog`, `User`).
- Baseline CRUD DRF ViewSets and standard ModelSerializers.

### Code Substantially Refactored or Engineered by Humans
- **`AssignmentService.py`**: Rewrote the assignment logic to ensure ordering is deterministic by user ID, active availability flags are checked, and database locks prevent race conditions.
- **`LifecycleService.py`**: Added the complete finite state machine validation preventing premature status jumps while requiring structured loss reasons on terminal attrition.
- **`api/client.js`**: Replaced standard Axios error throwing with a global interceptor that normalizes Django REST Framework nested error dictionaries into human-readable strings.
- **Accessibility & Focus Ring Hardening**: Refactored all common form primitives (`Input.jsx`, `Select.jsx`, `Button.jsx`, `ConfirmDialog.jsx`) to wire `aria-invalid`, `aria-describedby`, `role="alert"`, and keyboard `Escape` dismissal handlers.

## 5. Critical AI Mistakes, Detection, and Resolutions

The table below documents notable instances where AI-generated code was incorrect, how the issue was identified, and the engineering remedy applied:

### Case 1: Inadvertent Component Import Removal in `LeadDetailPage.jsx`
- **AI-Generated Error**: During Phase 15 UI polish, the AI attempted to clean unused badge imports in `frontend/src/pages/LeadDetailPage.jsx` and accidentally omitted the `Button` component import:
  ```jsx
  // Broken import:
  import { StatusBadge, AgeingBadge } from '../components/common/Badge';
  // Missing: import { Button } from '../components/common/Button';
  ```
- **How Identified**: Caught immediately during static analysis when running `npm run lint` (`Oxlint` flagged: `react(jsx-no-undef): 'Button' is not defined`).
- **Correction**: Re-imported `Button` from `../components/common/Button` and verified clean compilation.

---

### Case 2: Void `<input>` Tag Containing Children in `FollowUpsPage.jsx`
- **AI-Generated Error**: In `FollowUpsPage.jsx`, the AI generated a checkbox wrapped with child span text directly inside the input tag:
  ```jsx
  // Invalid JSX:
  <input type="checkbox">
    <span>Include Completed</span>
  </input>
  ```
- **How Identified**: `Oxlint` flagged: `Void DOM element <input> cannot receive children`.
- **Correction**: Converted the input into a self-closing `<input type="checkbox" />` enclosed within an accessible `<label className="flex items-center gap-2">` wrapper.

---

### Case 3: Email Uniqueness Constraint Causing Walk-in Intake Failure
- **AI-Generated Error**: The AI initially generated the `Lead` model with:
  ```python
  email = models.EmailField(unique=True)
  ```
  This failed when walk-in candidates without an email enquired, or when two siblings enquired using a shared parent email address. It broke Edge Case L (Missing Optional Data) with database integrity errors.
- **How Identified**: Discovered during the Phase 13 QA test suite execution when testing walk-in student registrations.
- **Correction**: Modified the schema to `email = models.EmailField(blank=True, default='')` with `db_index=True`. Replaced hard database uniqueness with non-blocking duplicate detection in `DuplicateService`, allowing admissions staff to make informed decisions.

---

### Case 4: Enum Naming Discrepancy in Activity Logging
- **AI-Generated Error**: The AI implemented lead reassignment by calling `ActivityType.ASSIGNED`, but the `ActivityType` enum class defined `ActivityType.COUNSELLOR_CHANGED`. This raised a runtime `AttributeError` during reassignment.
- **How Identified**: Caught by integration test `test_manager_reassign_counsellor` in `test_phase12_integration.py`.
- **Correction**: Standardized the event identifier to `ActivityType.COUNSELLOR_CHANGED` across both the service layer and the frontend timeline component.

---

### Case 5: Timezone Desynchronization in "Today's Follow-ups"
- **AI-Generated Error**: The AI filtered today's follow-ups using a naive string match:
  ```javascript
  const todayStr = new Date().toISOString().split('T')[0];
  const todays = list.filter(f => f.scheduled_at.startsWith(todayStr));
  ```
  Because the server stores UTC timestamps, a follow-up scheduled for 9:00 AM IST on September 25 is stored as `2026-09-25T03:30:00Z`, but an evening follow-up at 11:30 PM IST is stored as `2026-09-25T18:00:00Z`. In regions with positive UTC offsets, early-morning queries falsely matched the previous UTC calendar day.
- **How Identified**: Identified during manual integration testing when comparing backend `/api/follow-ups/?scheduled_at__date=...` query results with client-side filtered lists.
- **Correction**: Delegated date filtering to the backend Django ORM date filter (`scheduled_at__date=today_date`), which evaluates dates in the configured `TIME_ZONE = 'Asia/Kolkata'`.

## 6. Engineering Takeaways

1. **AI accelerates boilerplate, but domain rules demand rigorous tests**: While AI rapidly generated CRUD viewsets and React component layouts, core institutional business rules (deterministic round-robin, state transitions, and single-pass aggregations) required human oversight and test verification.
2. **Static typing and linters are indispensable AI guardrails**: Tools like `oxlint` and automated test runners caught 100% of hallucinations, missing imports, and invalid DOM nestings before code reached staging.
3. **Prompt specificity dictates architectural quality**: Asking AI for "clean code" yields generic solutions. Requesting explicit architectural patterns (e.g. "service-layer decoupling", "row-level locking", "WCAG AA :focus-visible") yields enterprise-grade production software.
